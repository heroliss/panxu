# 手动检查版本与后续便携更新方案

日期：2026-11-02。作者署名为 **Liss**；实际 GitHub 账号与仓库地址仍是 `heroliss/panxu`。本文区分本轮检查能力与后续安装设计，不改变 PolyForm Noncommercial 1.0.0，也不代表第三方材料的公开分发条件已经核对完毕。

## 本轮实现边界

**检查版本、下载安装、原子更新是三件不同的事。本轮只提供手动检查入口与只读版本适配器。**

| 能力 | 本轮边界 |
| --- | --- |
| 查看本机版本、作者与项目链接 | 从程序自己的版本与固定元数据读取，不依赖 LLM。 |
| 手动点击检查更新 | 当前发布源标记 `UPDATE_SOURCE_PUBLIC=False`；返回 `not_configured`，说明尚未提供公开更新源，无法比较版本。此路径不联网。 |
| 公开发布源适配器 | 为未来固定 GitHub Releases 公共接口准备，匿名请求，不带 token 或模型密钥，不接受模型提供的任意 URL；当前不开启或真实探测该源。本机 mock 不能证明远端已有可用发布包。 |
| 后台自动检查、下载与安装 | 未实现；不在启动或定时器中自动检查，不下载、解包、覆盖程序，不退出或重启应用。 |
| 外部 updater、数据库迁移与回退 | 后续设计，尚未交付。不能将本轮检查按钮描述为已经支持一键升级。 |

源代码仓库目前私有。没有公开可用的发布源时，检查结果必须是“尚未配置/无法比较”，不能报“已经是最新版”。未来启用的固定适配器目标是 `https://api.github.com/repos/heroliss/panxu/releases/latest`；启用必须以真实公开发布可用及相应授权为前提，不能只改一个布尔值就宣称交付。

未来公共接口请求有超时、响应体积上限、重定向拒绝和不少于 60 秒的结果缓存，避免反复点击连续请求；缓存不意味着自动后台查询。`404` 可能代表没有匿名可见资源，不能当作“没有更新”；限流、服务异常和网络失败也必须与“已核对无更新”区分。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)说明匿名访问适用于公共资源，不能据此推断当前私有仓库可匿名访问。

## 给普通用户的操作

本轮界面先显示当前版本和一个“检查更新”按钮。没有发布源时直接解释原因；有可信来源且确实核对成功后，才显示新版本号、简短说明和相应下一步。不把开发 JSON、token、安装流程细节放在默认界面，不要求普通用户填写 PAT。

后续即使增加下载安装，也应把“发现新版本”“下载完成”“已验证”“等待退出”“已更新”“已回退”分别表达。下载了 ZIP 不等于更新完成；进程能启动也不等于数据迁移和健康检查通过。任何失败都保留原程序及用户数据，并给出可重试或回退的明确状态。

版本比较使用经过校验的版本字段，不能按字符串排序；例如 `0.10.0` 大于 `0.9.9`。预发布通道、平台/架构、最低系统版本和最小 updater 版本须匹配。缺少必要字段、没有适用包或版本格式未知时，报告无法确认，不能补造“最新版”。

## 后续便携更新流程

以下是待实现方案；每一步都需要独立验收。

1. **取得与验证发布信息。** 从经过配置审核的固定 HTTPS 发布源读取有界 manifest。确认版本、平台、下载长度、解包上限与兼容要求；未来引入签名后，先验证签名再信任这些字段。不把 LLM 回复或任意下载链接作为更新授权。
2. **下载到隔离暂存区。** 下载不覆盖正在运行的程序。校验完整下载长度及散列，安全解包后核对固定文件清单；拒绝路径穿越、绝对路径、UNC、链接/重解析点、重复或大小写冲突名称以及超过预算的压缩内容。缺少 EXE、`_internal`、必要许可文件或校验失败时终止，不运行包内脚本。
3. **准备外部 updater。** updater 位于待替换程序目录之外，接收经过核验的固定参数和交接记录，不接受模型命令。用户明确选择更新后，应用先停止新任务、保存当前状态并正常退出；updater 等待所持进程句柄结束，同时区分 PID 与进程创建身份，避免 PID 复用。超时或文件仍被占用时放弃更新，不强杀其他程序。
4. **保留 userdata 并建立兼容快照。** 程序文件与用户数据分开管理，见下一节。所有应用进程停止后，对程序原版本与待迁移数据建立同一更新代次的快照，确认空间足够且快照可读。不能把不带 userdata 的发布 ZIP 覆盖解压到旧目录后就假定数据一定安全。
5. **暂存完整新版本，准备切换。** 优先使用独立版本目录和稳定启动入口，保留旧版本目录；新版本、完整性材料、兼容元数据与数据快照均已就绪后，再提交版本选择。文件切换必须留有可恢复的事务记录，不能把逐文件复制称为整个目录的原子更新。
6. **提交尽可能小的原子切换。** 候选方案是同一卷内原子替换经过校验的活动版本指针或启动器配置，使启动入口只指向完整旧版或完整新版。Windows 的文件替换 API 可作为单文件提交点的候选，权限、同卷限制、杀毒占用及错误恢复仍须验证；[ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)不等于整个多文件便携目录已经具备原子性。
7. **启动并核对健康。** 新版先在隔离的数据快照上验证 schema 与迁移，再进入受控首次启动。健康信号至少包括版本匹配、运行资源齐备、数据可打开、迁移完成、回环服务正常与原生界面可用；检查不能调用用户模型、扫描新范围、执行清理或重复历史动作。更新成功以完整健康检查结果为准，不能以进程创建成功代替。
8. **完成或回退。** 在明确提交成功前保留旧程序和兼容数据快照。失败时停止新进程，按事务记录恢复正确的程序与数据组合，记录失败阶段并重开可用版本。健康检查未完成时限制用户继续写入任务数据，降低自动回退丢失更新后新数据的风险；若已有新写入且不能无损合并，应保留两份数据并请求明确选择，不能静默覆盖。

这些步骤通常可在用户可写的便携目录、普通权限下完成。没有写入权限、空间不足、其他实例占用或包可信度不足时应停止，不以让整个应用永久管理员运行解决问题。

## userdata 与数据库回滚

当前默认 userdata 在程序目录旁，也支持 `--data-dir`。未来 updater 必须识别并保留实际数据目录，排除它的替换、删除和发布打包；不能把用户自定义目录改回默认位置。长期可考虑把 userdata 外置到独立可写目录，但迁移须显式执行、校验并保留旧位置，不能作为检查版本的副作用。

快照不只是几个数据库文件：还要覆盖同一代次的模型设置密文、偏好和其他有版本语义的本地状态，保留其隐私权限。模型密钥不写日志、不发给更新服务，不用解密出的模型密钥验证发布权限；DPAPI 密文保留也不表示换 Windows 用户或电脑后仍可解密。

SQLite 文件可能仍有 WAL 状态，不能在写入过程中只复制主 `.sqlite3` 并忽略 WAL，再声称备份一致。可使用 SQLite backup API 生成一致快照；多个数据库之间还需先停止业务写入并冻结同一代次，逐个数据库的一致性不自动等于整个应用状态的一致性。[SQLite 在线备份](https://www.sqlite.org/backup.html)与[WAL 说明](https://www.sqlite.org/wal.html)是实现依据，具体锁、迁移和回退方式仍需本机故障注入验证。

每次更新记录原/目标程序版本、原/目标 schema、快照指纹、迁移阶段与提交状态。存在两种回退情况：

- 新程序未改变持久 schema，且旧程序已验证可读取当前数据：可按已核对的兼容规则回退程序。
- 新程序已迁移数据，而旧程序不兼容：必须在所有相关进程停止后，恢复**原程序与同一代次的兼容数据快照**。只替换 EXE 会让旧代码读取新 schema，不能称为已完成回退。

迁移脚本须可重入或有明确的事务恢复点。事务内迁移失败不能标记 schema 已升级；跨库迁移、磁盘满、断电、锁冲突和首次启动崩溃都要覆盖。不得为清理更新备份而递归删除实际 userdata；旧快照保留与回收必须有单独、可审阅的策略。

## 完整性与作者身份

**SHA-256 只核对内容完整性，不是作者签名。** 如果发布包及其 hash 来自同一个被替换的来源，两者仍可能同时被攻击者更改；HTTPS 或 GitHub 链接本身也不能代替发布者签名验证。

未来可选择签名 manifest 并在已信任的程序中固定验证公钥，或验证 Windows 软件签名及预期发布者；需要明确密钥轮换、吊销、签名时间、版本回退与验证失败策略。manifest 不能自行提供一个新公钥再据此宣称自己可信。当前没有交付这些签名机制，不能把包内 hash 或署名 Liss 显示成已经验证的作者身份。

## 发布源选择与授权

当前私有代码库不提供公开更新源；不会内置个人 GitHub PAT、复用用户登录态或借用 LLM API Key。测试仅使用公开接口格式的本机 mock，不查询用户私有仓库或把云端鉴权失败隐藏成版本最新。

后续可以另设独立的公开 release 仓库，或使用受控 CDN manifest 与下载资源，同时继续保持源码仓库私有。这只是方案选项；未经明确授权，不创建公开仓库、不改变可见性、不发布安装包。真正启用前还要完成第三方再分发来源待办、发布源/签名/散列核对、匿名下载以及最终 Windows 产物验收。

## 后续验收条件

- 当前未配置源时，点击检查不联网、不更改模型或本地数据、不显示“已经最新”；失败和未配置与核对成功区分。
- 未来公开适配器在本机 peer 下验证版本比较、缺失/损坏响应、重定向、超时、体积上限、限流、缓存与无鉴权头，不能把这些结果描述成真实公共发布已通过。
- 实现下载安装后，再验证坏 hash、坏签名、路径穿越、解包超限、低磁盘空间、文件占用、退出超时与断电恢复，未完成前不开放自动覆盖。
- 实现迁移/回退后，验证旧程序与旧 schema、新程序与新 schema 成套匹配；清理备份不触及 userdata。真实个人数据不作为故障注入材料。
