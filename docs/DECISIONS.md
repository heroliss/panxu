# 设计决策记录

记录日期：2026-11-01。状态为本轮已采取的设计方向；未来条件满足时可以重访，但需记录新的证据与取舍。这里的产品决策不表示相关真实执行能力已经交付。

## D001：使用同一仓库作为长期代码基地

- **采取**：在本目录持续开发，保留设计、测试、实现与发布记录，通过 Git 和 GitHub 积累可审阅提交。
- **放弃**：每次对话另起一次性演示目录，或把工程与私人扫描输出混放后整体清理。
- **原因**：产品需要连续修复、回归验证和可追溯取舍，不能只保留某次可运行的产物。
- **重访条件**：确有模块独立发布、仓库规模或维护权限问题时，再明确迁移与历史保留方案。

## D002：正式面向普通用户，以渐进披露组织信息

- **采取**：先给用途、结论与影响，再展开技术依据；新手主流程与进阶明细共用同一真实库存。
- **放弃**：把原始路径表格、工具追踪与技术开关当作默认首页，要求用户自行扮演系统专家。
- **原因**：帮助理解和决策是产品职责，技术透明不等于默认展示全部实现细节。
- **重访条件**：真实可用性测试显示关键风险被隐藏时，增加必要提示；专业功能可扩展进阶视图，不反向压倒默认体验。

## D003：每个阶段只有一个主要 CTA

- **采取**：围绕“开始检查 → 查看建议 → 确认处理 → 记录”组织操作，目录、去重与设置作为次级入口。
- **放弃**：多个并列的大按钮和分散的确认入口，让用户不清楚下一步。
- **原因**：降低选择成本，保持一批操作范围与结果可理解。
- **重访条件**：出现明确不同的高频用户目标时，可增加任务入口，但需重新验证默认路径与作用范围。

## D004：由规则与证据守边界，由模型承担非个人判断

- **采取**：程序控制保护、范围、动作、预算和验证；LLM 提供结构化的非个人建议与白话解释。
- **放弃**：让 LLM 自由执行终端，或把所有项目都退回“你自己判断”，使模型只剩聊天包装。
- **原因**：既要减少用户负担，也要让模型建议受实际能力和可核查证据约束。
- **重访条件**：新动作具备明确契约、权限、核验和恢复测试后，可以作为受控能力加入；不能靠更长提示词替代执行层约束。

## D005：个人内容的最后选择权始终属于用户

- **采取**：下载、创建和用途未知文件保持个人组，不默认勾选；模型可解释、比较和建议动作。
- **放弃**：用模型分数、文件日期、扩展名或自定义要求自动替用户删除个人资料。
- **原因**：程序无法从元数据判断纪念价值、离线留存和未来用途；内容相同也可能分别承担路径引用。
- **重访条件**：用户建立明确、可撤销、限定用途的规则时，可设计单独授权流程；不能把一次“按建议处理”扩成永久授权。

## D006：缓存依据来自受管根验证，不能来自名称

- **采取**：当前采集器验证受管位置与 `decision_context`，默认选择还要求可再生成性和完整性证据。
- **放弃**：看到 Temp、cache、AppData 或旧日期就认定是垃圾；为兼容旧数据放宽默认选择。
- **原因**：普通下载目录可以拼出相同的路径片段，项目工作数据也会命名为 cache。
- **重访条件**：增加经过验证的缓存配方和应用适配器。旧目录快照需重检，不通过兼容层追认可信。

## D007：完整缓存目录根优先，避免默认选择所有叶子

- **采取**：经完整检查的推荐目录根作为默认操作单位；被覆盖子项保持推荐但取消重复自动选择。
- **放弃**：把几千个文件分别勾选、分别计量，再让用户处理计划条数超限或重复空间估算。
- **原因**：目录根更符合普通用户心智，也使批次范围更易审核。子项取消默认选择不等于变成个人资料。
- **重访条件**：子树包含个人、受保护、未知或未完整核查内容时，应拆分或保守阻断，不能为了方便坚持整目录处理。

## D008：以独立模拟覆盖层开发，不宣称真实释放

- **采取**：先验证真实只读库存、建议、计划和 UI；处理、撤销与记录仅修改 SQLite 覆盖层。
- **放弃**：早期直接接永久删除，或把界面上的模拟体积包装成实际释放量。
- **原因**：策略与交互需要反复验收；真实执行必须有单独的授权、恢复、失败和结果证据。
- **重访条件**：受限真实执行器、隔离与恢复协议、失败注入和 Windows 端到端验证全部完成后，建立独立发布阶段。不会用隐藏配置把当前版本切成真实模式。

## D009：模型输入最小化，决策输出结构化且有预算

- **采取**：结构化推荐最多 100 个代表候选，对话只给 3 个范围受限的只读工具；默认隐藏路径并严格验证 ID 与动作。
- **放弃**：整盘数据或文件正文上传、无限循环、把自由文本当作最终选择结果。
- **原因**：控制隐私、成本、延迟与越界行为，并能解释模型究竟覆盖了哪些项目。
- **重访条件**：有实际覆盖不足证据和明确预算时再设计分批任务；需要额外元数据必须说明用途和副作用，不静默增加外发范围。

## D010：密钥与服务来源绑定

- **采取**：Windows 用 DPAPI 保存用户密文；公共设置不回显；改变来源时明确替换或清除旧密钥，禁止静默复用。
- **放弃**：把密钥明文存入工程、日志或发布包，或者切换到另一服务商后沿用旧认证头。
- **原因**：配置修改不应成为凭据误发通道，本地应用也不应把调试异常当作凭据日志。
- **重访条件**：支持多提供方档案时，需为每个来源单独建密钥与权限模型，并保持迁移和清除语义明确。

## D011：重复内容是证据，不是自动删除许可

- **采取**：明确选择后执行有预算的本地 SHA-256 校验，区分硬链接、内容重复和路径用途。
- **放弃**：仅按文件名或大小宣称重复，或校验相同后自动删除副本。
- **原因**：模型、项目和备份可能依赖不同路径；逻辑重复也不保证能释放相同物理空间。
- **重访条件**：建立具体应用引用识别与恢复策略后，可提供更精细建议，仍需区分个人选择与受管副本。

## D012：Windows 能力逐项声明，不把枚举包装成控制

- **采取**：明确 Run、启动文件夹、CIM 服务、进程快照、传统桌面卸载注册项的覆盖范围；控制动作目前仅模拟。
- **放弃**：声称“全系统自启动优化”“所有软件卸载”“完整服务依赖分析”，或仅凭工作集高就结束进程。
- **原因**：不同入口、权限与依赖关系差异很大，局部清单不能证明系统全貌。
- **重访条件**：各适配器取得覆盖、权限和真实结果的独立证据后，再扩展能力声明。

## D013：数据留在本机，源码发布与用户数据分离

- **采取**：代码、设计、夹具和可复现构建材料进入仓库；数据库、私人路径、账号配置和原始验收材料默认留在本地。
- **放弃**：为方便复现把整份运行目录、个人截图或提供方配置上传 GitHub，或把已忽略文件视为历史中从未出现。
- **原因**：持久化状态本身包含隐私；发布与提交需要分别检查当前文件和版本历史。
- **重访条件**：确需共享诊断时，设计用户主动导出、字段脱敏与可预览流程，不能直接上传原始数据。

## D014：按最终产物验收

- **采取**：源码测试、真实 Windows 窗口、打包资源和最终构建散列分别记录；结果对应明确提交。
- **放弃**：仅凭源代码测试通过、页面能打开或打包命令成功就宣布产品完成。
- **原因**：桌面依赖、资源路径、运行状态和打包产物可能与测试环境不同。
- **重访条件**：验收可以自动化，但仍需覆盖最终用户实际拿到的产物，并保留未验证项。
