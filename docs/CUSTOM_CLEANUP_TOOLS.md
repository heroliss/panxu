# 自定义清理工具：可保存的规则与进阶适配器

日期：2026-11-02。状态：设计方案，尚未实现；不属于0.22.1已交付能力。当前仍仅有模拟执行器。本轮只记录架构与实现路线，不增加脚本执行、真实删除、后台定时任务或新UI。

## 目标与关键分层

用户或LLM可以把重复清理需求保存为工具。例如，用户描述“清理某软件Temp中超过7天未修改的tmp文件，保留Keep目录”，LLM生成结构化草案，程序以可读表单与匹配清单展示，用户保存。以后可本地运行，不需要再请求模型逐项判断或生成命令。

一份工具定义描述“如何找、如何处理”；一份运行计划记录“本次找到了谁、依据什么状态处理”。两者必须分开。定义长期复用，每次运行重新取证并冻结实际目标，不能重复执行上次的文件ID/清单。

首批可覆盖两类：已内置工具的固定参数预设；基于目录、文件名、大小/修改时间与排除项的文件清理规则。复杂系统/第三方操作后续通过脚本或原生适配器扩展，不要求穷举所有清理经验，也不让普通用户编写程序。

## 工具定义

- 稳定id、不可变版本/内容hash、名称、用途、类别、影响与恢复说明。
- 参数定义：类型、标签、默认值、枚举、必填、单位、可选路径范围，供UI与模型共用；用户填路径，不填shell片段。
- 类型：内置工具预设、文件规则、进阶脚本适配器。发现目录保持紧凑，按需读取完整定义。
- 文件规则：一个或多个已明确根目录、是否递归、包含条件/组合、排除条件、统一时间基准、匹配对象类型、具体动作及恢复策略。修改时间只能证明修改时间，不表述为最后使用时间。
- 来源：用户创建/模型协助、模型与生成时间、用户修改记录。来源是可核对的历史，不作为规则正确性的证明。
- 能力声明：诊断、准备计划、执行、逐项验证、恢复、进度、取消各自是否支持；未知、缺失与未实现分别表达。

内部定义可用版本化JSON保存于现有本地存储，产品UI显示自然语言摘要和表单。LLM通过严格原生工具参数创建草案，不靠自由文本里截取代码或JSON，也不下发HTML/JavaScript让UI执行。

## 一次运行

载入确定版本与参数 → 本地按需枚举/筛选 → 发布已观察对象 → 编译现有逻辑选择与排除 → 冻结实际计划 → 用户授权 → 原有执行/进度/逐项收据 → 保留区与历史 → 原任务结果回流。

目录规则先编译为具体文件动作，不把工具整体包装成一条“成功”而失去逐项身份和恢复记录。选择父目录时继续落实子项保留；匹配某些子文件不等于允许整删父目录。大量命中采用分页/分批与可取消扫描，部分检查不伪报全量，没有候选不混同为权限不足或扫描失败。

每次运行采用同一时间基准，并保留匹配解释。执行前检查实体、文件变化和占用；新变化项跳过或重新核对，不吞掉用户保留。链接、重解析路径与云占位等沿用已有范围处理，不能因路径看似在根目录内而扩大访问或下载正文。取消停止剩余项，已提交记录不伪称撤销。

保存工具不等于执行。常规运行直接使用本地规则，无需LLM重发命令。可逐步支持用户“信任此工具并减少重复确认”，授权绑定工具版本、范围、参数边界、动作和恢复方式；自然新增的匹配文件仍须按当次状态核验。变更上述内容展示差异并重新取得用户选择，不把信任扩展到任意后续脚本或其他磁盘。

## UI与LLM共用入口

- 工具箱内增加“我的工具”和“新建工具”；普通用户用表单，另有“让AI帮我创建”。不把脚本编辑器作为新手入口。
- 已有建议旁可按需提供“保存为清理工具”。用户选中的范围/排除项作为起点，LLM可补全有用条件并通过选项询问缺失偏好。
- 草案页重点显示名称、范围、包含/排除条件、动作、影响/恢复，以及只读试查的匹配数量和样本。按钮为“检查匹配”“保存工具”；“保存并运行”仍需进入本次具体计划。
- 保存后的工具复用当前工具详情：自动只读检查、已匹配数量/大小、查看完整清单、运行按钮、原有确认/进度/取消/记录/还原。没有匹配时禁用执行；未知或部分不当作0。
- 参数schema生成文件夹选择器、筛选条件、复选框等标准控件；模型决定建议内容与合适选项，宿主把tool_id/recipe_id及参数绑定到受控动作。
- 执行、拒绝、修改、取消、失败/部分/已验证结果，以及recipe_id、版本和run_id关联原任务。工具内容是用户数据，不成为改变宿主协议的系统指令。

候选模型接口可为草案创建/修改、完整定义读取、只读试查、提出保存/运行选项；名称后续与统一能力目录对齐。保存、运行与用户直接选择走同一应用服务，不建立一套只供LLM调用的执行器。LLM可发现用户工具，但不把整个脚本和历史运行日志预装进每次请求。

## 进阶脚本适配器

可以支持bat/PowerShell/指定可执行程序，但脚本是一类适配器，不等于整个自定义工具机制。需要准确的解释器/程序、参数边界、工作目录、版本hash、所需权限、输入输出、退出码语义、验证与恢复能力，避免把用户参数直接拼接成命令字符串。

对能遵守协议的适配器，可约定有版本的进度、逐项结果和最终结果事件；原始stdout/stderr放在可读的开发详情中，普通页面显示计数、状态和操作。对只有普通输出的脚本，进度应为未知/阶段状态，结束只代表进程退出；由验证器核实效果，缺失验证时记录“待核实”，不能强行映射成功。未提供恢复时不能显示“可还原”。

脚本进程可用Windows Job Objects管理超时及进程树取消；进程控制不等于文件系统/网络沙箱，终止进程也不会恢复已发生的修改。不得把PowerShell执行策略或-WhatIf当作任意脚本的模拟隔离。当前模拟模式只编译/显示定义并写模拟记录，不运行用户脚本后假称未修改系统，也不将未知脚本模拟成必然成功。

## 现有工程复用与缺口

- 复用FileCatalog的观察/逻辑选择、TaskHarness.prepare_assessment_plan、ActionRuntime、ExecutionControl、RecoveryStore和ToolActivity；运行收据携带工具来源，UI和模型读取同一事实。
- 现有CleanupToolkit依赖静态REGISTRY，cleanup_tool签名是版本与参数hash，尚无自定义定义的持久化、版本解析和文件规则编译。需增加定义解析层，让内置工具、预设、规则和脚本暴露一致的describe/inspect/prepare/execute/verify合同。
- 文件规则编译为已有文件动作，具体文件由既有运行时核验；不能为了接入方便直接复用只有工具级模拟收据的路径，随后向用户声称知道清理了哪些文件。
- 首版实现规则与内置预设的创建、试查、保存和模拟运行闭环；进阶脚本适配器、真实执行、持久授权和定时任务单独标状态并验收。手动反复运行不等于授权后台周期运行。

## 官方实现依据

以下仅为技术依据，不是本机事实或新增执行能力：

- Microsoft PowerShell execution policies：执行策略不是安全边界。https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies
- Microsoft ShouldProcess：WhatIf依赖命令/函数实现，调用链存在传递差异，不能代替宿主模拟路由。https://learn.microsoft.com/en-us/powershell/scripting/learn/deep-dives/everything-about-shouldprocess
- Microsoft Job Objects：进程组及子进程管理，可用于结束相关进程，不提供已发生文件操作的回滚。https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects
- Microsoft EnumerationOptions：枚举深度、递归、属性和访问失败的可配置选项；当前工程用Python，按原则复用现有扫描器，不因此改用.NET重写。https://learn.microsoft.com/en-us/dotnet/api/system.io.enumerationoptions
