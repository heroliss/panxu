# 盘序 1.0 设计说明

本文记录 1.0 重写时的主要取舍，供后续开发参考。功能和使用方法见 [README](../README.md)。

## 为什么重写

0.x 由 Codex 开发到 0.29，代码约 1 MB Python 加 1 MB JS，围绕「LLM 任务编排」设计：模型决定看哪里、调用工具、提出问题。但执行器始终只是模拟，从未删除过文件，也没有在真实环境里验证过清理效果。复杂度主要花在编排和界面状态上，清理本身的价值很少。

1.0 的方向（2026-11-03 与维护者确认）：

- 技术栈保持 Python + pywebview（WebView2）+ HTML/JS，PyInstaller 打包。
- 删除策略按类别区分：规则已知的系统和应用缓存直接删除；个人文件（大文件、重复文件、用户选择的文件夹）移到回收站；每次操作都记录。
- 1.0 范围：垃圾清理、空间分析、大文件和重复文件、开机启动项和服务。
- AI 采用混合模式：程序掌控流程，明显的情况由规则决定，模型只对规则不认识的大文件夹做分类，并且可以对整个文件夹下结论而不必逐个文件询问。

## 前后端通信：pywebview js_api，不用本地 HTTP 服务

0.x 在 127.0.0.1 上开了一个 HTTP 服务。对一个能删除文件的程序，这意味着本机任何进程、以及通过 DNS 重绑定的网页都可能调用删除接口。1.0 改为 pywebview 的 js_api 桥：只暴露一个方法 `Bridge.call(method, params)`，内部分发到 `Backend.m_<method>`，返回值统一为 `{ok, data | error}`。界面由 `ui_bundle.build()` 内联成一个 HTML 字符串，通过 `create_window(html=...)` 加载，不需要文件服务器。

长任务（扫描、清理、AI 分析）在后台线程运行，界面每 300 毫秒轮询一次 `job` 状态。轮询比从 Python 端调用 `evaluate_js` 推送更容易测试，也不会碰到跨线程调用窗口的问题。修改类任务属于同一个互斥组，不会同时运行两个删除任务。

## 删除的安全边界

| 层 | 位置 | 作用 |
|---|---|---|
| 规则目录 | `junk.validate_catalogue` | 测试中静态检查每条规则的目标都位于已知基础目录之下，且不是基础目录本身 |
| 运行时根目录检查 | `junk.unsafe_root_reason` | 解析出的清理根目录不能是盘符根、不能包含用户文件夹或系统目录；来自 %TEMP% 的根目录必须名为 Temp/tmp |
| 保护策略 | `paths.ProtectionPolicy` | 用户和 AI 选择的路径：受保护子树内的不能删，基础文件夹本身不能删，包含受保护或排除文件夹的上级目录也不能删；对原路径和解析后的真实路径都检查一次 |
| 遍历 | `fsops.walk_files` / `st_is_link` | 不进入名称代理类重解析点（目录联接、符号链接）；OneDrive 云文件的重解析点会正常进入；无法判断的一律当作链接 |
| 回收站 | `winapi.recycle_paths` | SHFileOperationW 带 FOF_ALLOWUNDO 和 FOF_WANTNUKEWARNING：放不进回收站时由 Windows 询问 |

文件「年龄」在 Windows 上取修改时间和创建时间中较新的一个，因为从压缩包或安装程序里解出的文件常常带着很旧的修改时间。

## 空间扫描

扫描器只为目录建立节点（`__slots__` 对象），文件只累加到所在目录；另外保留全盘最大的 5000 个文件，供大文件页面使用。打开某个目录时，它自己的文件再实时列一次。这样一块有几百万个文件的磁盘也只占几十 MB 内存。

多个线程从同一个队列取目录。子节点总是在父节点之后追加到列表，所以扫描结束后倒序遍历一次就能把大小汇总到上层，不需要加锁。在 Windows 上 `DirEntry.stat()` 的结果来自 FindFirstFile，本身不额外访问磁盘。

已知限制：显示的是文件的逻辑大小。压缩文件、稀疏文件和 WinSxS 里大量的硬链接会让显示值大于实际占用（WinSxS 的说明里已经提示）。

## AI 分析流程

`analyst.Analyst.analyze_space` 的步骤见 README。几个具体选择：

- `knowledge.Knowledge.ai_role` 把路径分成 skip（已知，不问）、descend（结构性文件夹，展开看子文件夹）和 ask（发给模型）。个人文件夹属于 skip，既节省额度，也不把个人目录名发出去。
- 每个请求要求模型只返回一个 JSON 对象。支持时开启 JSON 模式，服务端返回 400 时自动关闭重试；解析失败会带提示重试一次。
- 模型返回的 verdict 不在允许范围内时一律当作「需要你确认」；`look_into` 只接受摘要里真实存在的子文件夹名。
- 401/402/403/404 这类配置错误会立即停止，不继续消耗请求预算。
- 结果按匿名化后的路径缓存 30 天；文件夹大小变化超过一倍时缓存失效。

AI 建议默认移到回收站；勾选的初始状态只包括「可清理」且把握不低于 75% 的项目。

## 开机启动项

列出注册表 Run（当前用户、所有用户、32 位）和两个启动文件夹。启用或禁用通过 Explorer 的 StartupApproved 标志完成，和任务管理器的「启动应用」使用同一套开关，原有的 Run 项和快捷方式不会被删除或改动。修改「所有用户」的项目需要管理员权限。以另一个管理员账户提权时，HKCU 属于那个账户，所以当前用户的项目只读。

服务只允许修改第三方服务的启动方式（`sc.exe config`），Windows 和微软的服务只显示。每次修改都在操作记录中保存原来的值，可以撤销。

## 尚未实现 / 后续可以考虑

- 应用商店应用的启动任务、带登录触发器的计划任务只能在系统设置里管理，1.0 不列出。
- 休眠文件（powercfg /h off）、虚拟内存大小、系统还原点占用只给出说明，不提供一键操作。
- Docker / WSL 虚拟磁盘的压缩只给出说明。
- 直接读取 NTFS 主文件表（类似 WizTree）可以把扫描提速一个数量级，但需要管理员权限，而且无法在当前的开发环境中测试，暂未实现。
- 以另一个管理员账户提权时，用户文件夹的重定向位置按管理员账户解析。
