# 盘序设计说明

更新日期：2026-11-02。本文记录产品方向、实现边界和后续开发的依据。具体接口以 `CONTRACT.json`、实现和自动化测试为准；规划中的能力不算已经交付。

## 方向更新：围绕 LLM 的任务循环

2026-11-02 按用户最新讨论，将下一阶段主方向调整为 **LLM 驱动的整理智能体**。LLM 根据需求决定如何调查、提出计划、解释取舍，并根据用户选择和工具结果继续工作；程序提供可靠事实、经验、操作能力、会话支持和针对任务的 UI。常见清理规则作为可调用的经验与工具继续保留。

详见 [智能体架构提案](AGENT_ARCHITECTURE.md)。下文的固定扫描入口、推荐规则和工具限制同时描述当前 v0.2.0 实现，不能视为未来智能体能力的永久上限。下一阶段优先补充“取得新证据并继续”的能力，避免证据不足就只能让用户自行判断。身份、用户已明确的保留意愿、实际权限、外发范围和结果真实性仍需由程序落实。

v0.3.0 实施状态：整理助手已使用独立的持久任务循环，支持 9 种调查/方案工具、用户反馈、版本化审阅、逐项模拟核验和结果回传。下面的固定扫描与旧顾问限制继续适用于基础检查入口；尚未实现的能力与工具见架构文档，不以旧接口能力上限限定新任务方向。

## 长期代码基地

本目录是盘序的长期代码基地，不是一次性演示、扫描输出目录或可随清理任务删除的临时副本。后续功能、修复、测试、设计变更和发布工作应持续在同一仓库积累，并通过 Git 提交保留可追溯的版本。

`docs/DESIGN.md` 说明产品与架构；`docs/DECISIONS.md` 记录取舍和重访条件；`docs/ROADMAP.md` 区分已实现与计划。设计改变时，应在相关实现提交中同步记录原因。GitHub 是源码协作与版本载体，不是个人扫描结果、账号配置或运行数据库的备份地点。

## 面向谁，以及替用户承担什么

盘序面向希望整理 Windows 11 空间与后台、但不熟悉系统目录和程序依赖的普通用户。用户不应先学习一堆技术字段，再自己判断每个缓存、服务和启动项的作用。

产品应尽量直接说明“它是什么、建议怎么做、为什么、会有什么影响”。对非个人内容，规则和模型负责完成有依据的判断；证据不足时明确指出缺口，而不是假装已确认安全。个人下载、创建或用途未知的文件，模型可以解释和提供去留建议，最终是否处理仍由用户选择。

这里的“建议处理”不等于已经执行，也不等于没有副作用。界面必须把建议、计划、执行结果和恢复能力分别表达清楚。

## 主流程与渐进披露

v0.3 默认主流程为：**表达目标与范围 → 模型按需调查 → 审阅或调整方案 → 确认处理与核验 → 继续或结束**。

- 首页呈现用户目标与一个文件夹范围，主要行动为“开始分析”。模型在当前范围按需选择调查工具。不要默认遍历全部磁盘，不以开发样例冒充本机结果。
- 任务先呈现当前结论与少量方案卡片，明确动作、原因和个人选择要求。基础检查继续使用“建议处理”“你的文件”“建议保留”等分组。
- 同一阶段只有一个主要 CTA。结果页的主要动作应围绕当前建议批次；目录选择、重复校验、技术明细和模型设置作为次级入口。
- 默认卡片说明具体用途，例如 Python 下载缓存、图形着色器缓存、某应用的开机启动功能，而不是只显示“低风险”或“建议处理”这样的类别名。
- 原因与影响放在用户容易看到的位置；路径、来源、身份签名、预算、计量和工具追踪等技术依据按需展开。
- “我的文件”和“后台与软件”的完整清单供需要精细控制的人使用。不能要求所有新手先看懂原始表格，才有办法完成主流程。
- 推荐缓存优先以经过完整核查的目录根作为处理单位。已被该根覆盖的子项不重复默认勾选，仍保留推荐身份和明细，避免几千个叶子文件淹没界面与计划预算。

产品界面按正式应用设计。开发阶段的模拟保护应持续可见，但不应把整个产品永久做成演练台。真实执行器完成前，确认按钮附近和结果中必须明确说明当前只写模拟记录。

## 当前 v0.2.0 的建议规则

判断的优先级是：**保护与能力边界 → 本机证据 → 个人决定权 → 模型建议 → 默认选择**。

1. 系统、凭据、用户保护规则、没有支持动作的项目，以及已经处理的模拟条目，不能被模型重新开放。
2. 缓存默认推荐必须来自采集器验证的受管位置与可再生成性证据。当前实现使用 `verified_cache` 和 `decision_context`；目录还需要完整子树检查。仅凭名字含 cache、Temp，或路径拼出了 AppData 字样，不构成证据。
3. 下载、创建或用途未知的用户文件保持个人选择。模型的理由、置信表达和自定义要求都不能取消 `needs_user_choice`。
4. 后台或软件只有在本机有充分的正向证据，并且模型明确提出相应建议后，才可能进入推荐。高内存、旧时间、第三方厂商或旧版本号本身都不证明无用。
5. 模型可以使本地缓存推荐变得更保守；占用、链接、扫描不完整等限制不能靠一个泛化的证据标记重新放行。

原始库存字段与 `advice` 分离。建议改变不应悄悄改写原始用途、风险、允许动作或系统状态。

## 当前 v0.2.0 的处理契约

当前已实现的程序化处理流程为：

**采集 → 归一化库存 → 保护与证据判断 → 建议 → 冻结计划 → 再验证 → 受控动作 → 结果核验 → 记录。**

- 采集器负责有限范围的文件元数据、Windows 注册信息和运行快照，不把文件名或扫描内容当指令。
- 规则层负责硬保护、个人选择、动作能力、证据有效性和计量，模型不能修改这些边界。
- LLM 负责用途解释、非个人内容建议、取舍与影响说明。结构化输出必须通过 ID、动作、范围和字段验证，不能从自然语言里抽取一个“删除”就当成授权。
- 计划绑定库存版本与具体项目。系统状态变化、路径身份变化或扫描不完整时应重新检查，而不是沿用旧快照。
- 动作使用有限的类型，例如文件处理、启动项调整、服务控制、进程停止与正规卸载。动作类型的存在不代表真实执行器已经实现。
- 执行器、授权、核验和恢复协议应由程序掌握。模型不能批准计划，不能执行任意 shell，不能读额外文件或绕开执行策略。

## 当前实现与开发覆盖层

当前构建可以读取真实库存，但**所有处理动作仅写入本地 SQLite 模拟覆盖层**。没有真实删除、移动、停止进程、控制服务、禁用启动项或卸载程序的执行器，也没有可开启真实执行的隐藏开关。

冻结计划、保护检查、模拟执行、撤销和记录已用于验证产品流程与策略。记录里的撤销只还原工具内部状态，不能解释成已经具备真实文件恢复能力。模拟处理后的实际释放量始终为 0。

空间展示分别使用以下概念：

- 真实磁盘空闲量：只读查询当前磁盘，可能受到其他程序同时写入的影响。
- 文件逻辑体积：用于理解项目大小，不保证与实际占用、可回收量一致。
- 分配空间与硬链接：能取得的证据单独展示，未知时不编造精确值。
- 进程工作集：运行快照，可能包含共享页，不等于停止后能释放同等物理内存。
- 模拟体积：仅表示本地记录中的处理范围，不能与真实空闲量相加或宣称已经释放。

## 现有采集、去重与记录

文件扫描有目录深度、条目数和任务预算，不跟随重解析点，保守保护项目、凭据及系统内容。用户文件目录由用户明确选择；不完整目录不能作为整组处理目标。

Windows 采集覆盖当前实现支持的 Run 注册项、启动文件夹、服务、进程和传统桌面卸载注册项。它不是所有自启动位置、所有 Store 应用、完整服务依赖图或实时文件锁的审计。Run 注册项也不能单独证明任务管理器中的实际启用状态。

重复校验只针对明确选中的文件，在预算内读取字节计算 SHA-256，并检查快照变化。普通盘点和模型上下文不读取文件正文；重复校验是本地哈希这一明确的例外，不会把字节内容发送给模型。硬链接另作解释；内容相同不等于可以自动删除其中一个副本。

本地记录包含计划、模拟处理和撤销状态。后台任务与结果有边界，失败或被取消不能伪装成完整检查。未来真实执行结果应继续沿用可核查记录的原则，但不能把现有模拟记录当成真实恢复日志。

## 模型能力、预算与数据私有

未配置模型时使用本地规则，不联网，不显示成“AI 已完成分析”。配置模型后，可以通过 Chat Completions 兼容服务取得结构化建议；这不代表兼容每家服务商的专有参数。

- 单次结构化推荐最多发送 100 个有代表性的候选。只统计通过验证的建议覆盖，遗漏与失败明确报告，其余保持本地结果。
- 对话解释最多 4 轮、8 次工具调用。模型只能查询本次提供或选中库存的 `list_items`、`inspect_items`、`summarize_inventory`，不能扩展扫描范围。
- 请求有超时、请求体和响应体预算。未知工具、越界 ID、错误动作、额外决策字段或不合格输出被拒绝。
- 默认不发送完整路径，也不发送文件正文、原始证据内容、账号数据库、进程命令行和环境变量。允许的元数据仍可能包含文件名和用途等私人线索，用户启用远程模型前需要理解这一点。
- Windows API Key 使用当前用户 DPAPI 密文保存；非 Windows 仅驻留内存。公共接口不回显密钥，更换服务来源必须明确替换或清除旧密钥。
- 远程接口要求 HTTPS；HTTP 仅限回环服务，拒绝带认证信息的 URL 和重定向。不记录模型对话正文，不用异常原文泄露凭据。

自定义模型要求是偏好，不是新的执行权限。提供方的数据留存政策不是本地程序能保证的，应在接入界面解释清楚；默认路径隐藏也不等于“完全没有私人元数据外发”。

## Windows 范围与发布边界

产品目标是 Windows 11 本地桌面使用，通常以普通用户权限运行。Python 标准库构成核心，桌面窗口和部分运行盘点使用相应依赖；桌面 WebView 不可用时可以退回本机浏览器。非 Windows 单测通过不构成跨平台功能支持。

本地 HTTP 服务只监听回环地址，校验 Host、Origin 和修改请求的 CSRF；静态资源采用白名单，不从 CDN 加载应用代码。正式执行能力即使将来引入，也不应让整个应用长期默认提权。

源码、设计、测试夹具和可复现构建脚本可以进入仓库。运行数据库、真实扫描路径、个人截图、原始验证数据、模型配置、密钥及其他用户数据必须留在本机；发布包只带运行所需代码与资源。记录版本、测试结果和构建散列时，应使用不暴露私人路径或内容的证据。

每个发布版本都应能回答：对应哪个提交、运行了哪些验证、哪些能力是只读或模拟、哪些真实行为尚未实现。源码测试通过不自动证明打包后的 Windows 窗口和最终产物通过验收。
