# 盘序 Harness 沟通设计研究

核对日期：2026-11-02。范围为第一方工程文章、官方 API 文档，以及候选技能的作者仓库。仅做只读研究，没有安装技能、运行第三方脚本或调用用户配置的云模型。以下是对盘序的工程推导，不能当作厂商模型在本机的实测效果或本轮功能完成证明。

## 结论与本项目的对应

### 1. 让模型做判断，让宿主维护阶段与可达性

模型应回答“下一步要了解什么、已有证据支持什么建议”，不必同时管理内部来源版本、预算计数及调用协议。已知任务和对象范围应由宿主传递；模型只能选择真实可用的能力。OpenAI 的函数设计指南建议把已知参数和固定组合步骤交给代码，明确工具的用途、输入和返回含义；工具数量需按评估结果控制，而不是把“少于20”当成硬标准。[官方函数设计指南](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)

盘序对应：`tasks.py` 目前以6次响应/12次工具为宿主边界，末两轮切换为评分和收束。应从同一阶段描述生成可用工具和发给模型的提示，避免提示仍要求 `read_facts`，实际 `FINAL_TOOLS` 却移除此工具。读取已有事实与采集新的电脑事实也应分别分类，不能因为停止新采集而同时切断持久证据。这里是基于0.20代码的风险识别；本次失败是否由它触发，仍以实际任务 trace 为准。

### 2. 少而明确的工具，加上可纠正的错误

Anthropic 的工具设计经验强调清楚的职责、相关结果、合理分页和能指出修正方式的错误，而非把每个程序内部端点都作为独立模型工具。它也明确表示不同响应格式需按任务实测，没有普适最优格式。[工具设计原文](https://www.anthropic.com/research/writing-tools-for-agents)

盘序对应：保留扫描、读取、分析记录等自然动作，减少多个相似“发现/读取/检查”之间的猜测。工具说明写明“何时用、返回哪些信息、下一步如何继续”；错误保留稳定代码、具体字段与合法替代动作。对未知ID，提示从哪个当前列表取得ID；对页面上限，返回可继续的游标/更小范围。不要把所有错误都退化成“参数或结果无效”，也不要为修复错误自动扩大授权或执行范围。

### 3. 小型开场上下文，按需正文，压缩后仍能继续

Anthropic 的上下文工程文章支持轻量引用与按需加载，也讨论先提供少量必要资料的混合方式；最短上下文本身并不是目标。[上下文工程原文](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

盘序对应：新任务先给目标、授权位置、用户保留/拒绝、适用能力，以及简短当前状态；大目录仍由模型逐层调查。当前轮工具的有用实体结果应保留到评分阶段。压缩与换模型时保存“已知结论、证据引用、关键实体、未解决问题、下一步”，并保证正文可由当前工具读取。仅留下事实ID/工具名但不提供内容或可调用的读取途径，会把节省 token 变成重新调查或无法判断。历史时间、未知/0/false和作用范围不能因压缩混淆。

### 4. 简化业务输出，保留可靠的机器协议

面向用户的说明可以是自然语言，模型写回建议则继续使用原生工具参数。OpenAI 的严格模式对 schema 有明确要求，包括对象禁用额外字段及必填字段约束；这些是特定 API 的能力，不能假定所有兼容端点都支持相同选项。[函数调用严格模式](https://developers.openai.com/api/docs/guides/function-calling#strict-mode)

盘序对应：模型仅填写分析真正需要的名称引用、倾向、用途、原因和影响；任务ID、来源绑定、时间、版本和签名由宿主补齐。用枚举与单一语义字段减少无效组合；不要让模型手写整份内部计划或权限结构。四协议适配继续留在连接层，调用ID/结果配对、流式片段完整性和 schema 校验由程序处理。严格参数校验不能代替对象权限和执行确认。

### 5. 把用户直用工具形成精简活动记录，交给模型按需理解

长任务需要外部持久状态和清楚的续接记录；仅依赖聊天压缩容易丢失工作状态。Anthropic 的长任务 harness 文章展示了进度记录与端到端验证的价值，原文场景主要是软件开发。[长任务 Harness 原文](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

盘序对应推导：用户直接使用系统清理工具无需模型批准或重新规划，程序记下提出建议、拒绝/暂缓、确认、打开入口、实际/模拟执行及核验结果。模型下一次获得简短最新摘要，详细记录可按需读取。`opened`、用户说“已完成”、本机观测确认和模拟收据应分别表达，不能把打开系统窗口写成已清理。拒绝也要记录来源与范围，避免下一轮重复建议；临时暂缓不自动变成永久保留。这个活动记录不授予额外处理权限。

### 6. 用真实失败轨迹回放衡量改善，而不是只数合法工具调用

OpenAI 的评估指南将工具选择、参数精确性及最终任务结果分别评估，并建议随着发现新问题持续扩大回归集。它不建议在缺少评估依据时先堆多智能体架构。[评估最佳实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

盘序对应：将本次脱敏失败转换为离线轨迹夹具，覆盖恢复任务只有历史引用、压缩临界点、收束阶段证据读取、参数错误修复、分页未完、用户拒绝工具及手动执行结果回流。成功标准是能生成有依据的评分/结论或清楚指出真实缺口，并保留保护与范围；不能只验证最终状态变成completed。额外记录模型可见字符/估算token、重复采集次数、修正轮次、评分覆盖和总延迟；没有提供方usage时不伪造精确费用或token节省率。真实云模型复测需另外标明，离线回放不冒充云端效果。
